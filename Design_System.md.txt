# PlacementIQ — Design System

PlacementIQ should look like a professional, modern college placement intelligence platform rather than a generic AI dashboard. The design should make it easy for students to understand their readiness, faculty to conduct assessments, and placement officers to track overall placement preparation.

The recommended direction is light-first, clean, data-rich, and approachable, with a restrained blue-and-teal palette, clear typography, consistent cards, and simple navigation.

Usage rules

- Use primary blue for the main action on a page, not every button.
- Use teal as an accent, not as a second dominant brand color.
- Use red only for errors, failures, or genuinely critical states.
- Pair status colors with text labels and icons.
- Avoid gradients on every card, neon colors, and dark backgrounds across the application.

## 3. Typography

Use Inter as the primary font. It is clean, readable, and suitable for both dashboards and assessment interfaces.

| Element             | Size     | Weight  |
| ------------------- | -------- | ------- |
| Page title          | 28–32 px | 600–700 |
| Section heading     | 20–24 px | 600     |
| Card heading        | 16–18 px | 600     |
| Body text           | 14–16 px | 400     |
| Labels and metadata | 12–13 px | 400–500 |
| KPI number          | 28–36 px | 600–700 |
| Buttons             | 14 px    | 500–600 |

Use sentence case for headings, such as “Student readiness overview,” rather than writing everything in uppercase. Reserve tabular numerals for scores, counts, timers, and percentages.

## 6. Product navigation and page patterns

Use role-based navigation. The interface should reveal relevant tools without overwhelming users with every platform feature.

| Role              | Main navigation                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| Student           | Dashboard, My Skills, Coding Practice, Assessments, Mock Interviews, GitHub Analysis, Improvement Plan |
| Faculty           | Dashboard, Student Directory, Interviews, Question Bank, Test Builder, Results                         |
| Placement officer | Overview, Students, Readiness Distribution, At-Risk Students, Reports, Placement Outcomes              |
| Administrator     | Users and Roles, Departments, Assessment Settings, Integrations, Audit Logs                            |

Recommended page patterns:

- Dashboard: KPI cards, readiness distribution, recent activity, and a short list of recommended actions.
- Student profile: profile summary, skill breakdown, assessment history, interview feedback, verified GitHub evidence, and improvement plan.
- Interview studio: candidate context, interview stage, question area, timer, notes, and evaluation panel.
- Test builder: question library, difficulty filters, selected-question list, test settings, preview, and publish action.
- Analytics: cohort filters, distribution charts, detailed student tables, and export controls.

## 7. L1, L2, and L3 visual treatment

Keep the levels visually consistent and make their definitions accessible wherever they appear.

L1 — Foundation

Developing fundamentals, basic problem-solving, and confidence.

Foundation

L2 — Developing

Applying concepts, solving intermediate problems, and explaining approaches.

Developing

L3 — Placement ready

Demonstrating consistent performance across the defined assessment criteria.

Advanced

Important: do not determine a student's level from coding score alone. Base it on the platform's documented scoring rules and sufficient assessment evidence. Show students why they received a level and how to improve it.

## 8. Charts and data visualization

Use charts only when they help users make decisions.

- Bar charts: compare student groups, skills, or departments.
- Line charts: show readiness and assessment progress over time.
- Horizontal bars: show individual skill scores and skill gaps.
- Donut charts: show cohort readiness distribution when there are only a few categories.
- Tables: support exact comparisons, searching, sorting, and follow-up actions.

Avoid 3D charts, excessive gradients, too many colors, and charts without labels. Include tooltips, accessible legends, and a tabular alternative when the data is important.

## 9. AI interview and assessment design

These screens need their own focused layout while retaining the shared design system.

AI Interview Studio

- Display the interview type, duration, difficulty, and candidate context at the top.
- Separate the question, response area, and evaluation notes.
- Make timer and interview controls prominent without dominating the screen.
- Clearly identify AI-generated questions and provide faculty override controls.
- Keep private evaluator notes separate from student-visible feedback.
- Show when an evaluation is pending, completed, or requires faculty review.

Test Builder

- Use a two-panel layout: question library on the left and selected questions on the right.
- Show question type, topic, difficulty, and marks as compact metadata.
- Include a test preview before publishing.
- Confirm before deleting questions or publishing an assessment.
- Provide visible progress for saving, publishing, and processing results.

## 10. Responsive behavior and accessibility

- Desktop: full sidebar and multi-column dashboards.
- Tablet: collapsible sidebar and fewer columns.
- Mobile: compact header, drawer navigation, single-column cards, and horizontally scrollable tables where needed.
- Keep critical actions visible and avoid placing primary actions below long content unnecessarily.
- Support keyboard navigation, visible focus indicators, meaningful labels, and screen readers.
- Aim for WCAG 2.2 AA contrast and accessibility practices.
- Provide loading skeletons, empty states, error recovery, and confirmation messages for important actions.
- For timed assessments, make remaining time readable and warn users before expiry.

## 12. Final design rules

1. Keep the application light-first and consistent across all roles.
2. Use blue for primary actions and teal for positive progress.
3. Prefer simple cards, clear hierarchy, and useful whitespace.
4. Keep all spacing, typography, borders, and button sizes consistent.
5. Prioritize real information over decorative visual effects.
6. Never display fabricated readiness scores or imply AI assessments are infallible.
7. Ensure every chart, status, and recommendation has a clear meaning.
8. Build reusable components before implementing all dashboards.
9. Design mobile and accessibility behavior as part of the initial system.
10. Keep the experience focused on measurable student improvement, not merely attractive analytics.

Recommended implementation order: establish the color and typography tokens, build the application shell, create the shared component library, then implement the student dashboard, faculty assessment tools, and placement analytics. This will make PlacementIQ feel like one coherent product rather than a collection of separate screens.
